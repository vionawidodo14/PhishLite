<p>For those that have been keeping an eye on Web Design Weekly, you probably have noticed that things have been extremely quite… ?</p>
<p>The first half of the year was quite productive. Lots of new articles, a range of site modification and great newsletter growth. It was shaping up to be a great year until August arrived. During the first half of the year my full-time job was pretty quiet so I had the motivation and energy to tinker and work on WDW in the evenings. That all changed pretty quick when we landed an awesome project at work and I was knee-deep in some pretty interesting development. </p>

<span class="posted-on"><time class="entry-date published" datetime="2016-07-01T09:01:05+11:00">July 1, 2016</time><time class="updated" datetime="2016-07-01T09:04:04+11:00">July 1, 2016</time></span><span class="byline"> — <span class="author vcard">Dennis Gaebel</span></span> </div><!-- .entry-meta -->

<!-- show full post content if a link post -->
<p>If you’re still writing JavaScript using <a href="http://www.ecmascript.org/docs.php">ES5</a> (also known as ECMAScript 5) and desire to author in ES6 (ES2015) fear not. We’ll look over some logical ways to start using this new syntactical sugar in your own work starting immediately. We’ll discuss and examine approaches to integrate features such as <code>let</code> and <code>const</code> plus compare <code>var</code> versus <code>let</code> and finally understand when to use the spread operator. </p>

<h1 class="entry-title"><a href="https://web-design-weekly.com/2016/06/15/integrate-stylelint-workflow-better-css/" rel="bookmark">Integrate Stylelint Into Your Workflow For Better CSS</a></h1>
<div class="entry-meta">
<span class="posted-on"><time class="entry-date published" datetime="2016-06-15T12:45:24+11:00">June 15, 2016</time></span><span class="byline"> — <span class="author vcard">Jake Bresnehan</span></span> </div><!-- .entry-meta -->
</header><!-- .entry-header -->
<div class="entry-content">
<!-- show full post content if a link post -->
<p>Working within a team or solo can adjust the development priorities but one that should always be high on the agenda is producing the best code possible.</p>
<p>Working on a clean, well organised codebase is bliss. It’s enjoyable and productive. Working on an unorganised codebase is annoying to say the least. It’s often frustrating, painfully slow to change and test anything and invites laziness.</p>
<p>Thankfully as CSS developers we have a handy tool called <a href="http://stylelint.io/">Stylelint</a> that can help us avoid the unorganised situation. </p>

<article class="post-70679 post type-post status-publish format-standard hentry category-link" id="post-70679">
<a class="link-post-title" href="https://marcelosomers.com/writing/rationalizing-functional-css/">Rationalizing Functional CSS</a>
<p>This post by Marcelo Somers looks at the good and bad parts of writing functional CSS.</p>
<blockquote><p>I loved writing really clever, powerful CSS classes. I argued for it because of “ease of developer consumption.” My goal was that a developer could add a single class to an element and it would automagically do everything for them. Basically, the opposite of functional CSS.</p>
<p>3 months into a functional approach to CSS architecture, I’m addicted. The times I’ve used the old monolith approach, it’s become a tedious challenge in jumping between files constantly. I think I’m convinced, but I’m still trying to rationalize scalability issues as my functional codebases grow and evolve.
</p></blockquote>
<p>I’m a massive fan of functional CSS and would highly recommend experimenting.</p>
</article>
