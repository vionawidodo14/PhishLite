<h2><a href="https://nolanlawson.com/2019/09/22/the-joy-and-challenge-of-developing-for-kaios/" rel="bookmark">The joy and challenge of developing for KaiOS</a></h2>
<p class="metadata">
	Posted by Nolan Lawson in <a href="https://nolanlawson.com/category/webapps/" rel="category tag">Webapps</a>.	Tagged: <a href="https://nolanlawson.com/tag/kaios/" rel="tag">KaiOS</a>.	<span class="feedback"><a href="https://nolanlawson.com/2019/09/22/the-joy-and-challenge-of-developing-for-kaios/#comments">5 Comments</a></span></p>
<div class="entry">

<p>Recently I spent some time getting <a href="https://pinafore.social">Pinafore</a> to run on a <a href="https://www.kaiostech.com/">KaiOS</a> device. Overall, I found it to be challenging but enjoyable. In this post, I’ll talk about some of the tricks that helped me to work with this curious little feature phone.</p>
<p>Why KaiOS? Well, I guess I’ve always been a bit of a gadget geek. I’ve been developing for Android since the early days of the <a href="https://en.wikipedia.org/wiki/HTC_Dream">HTC Dream</a>, I managed to get my Nexus 5 to <a href="https://github.com/nolanlawson/nexus-5-triple-play">triple-boot into Android, Firefox OS, and Ubuntu Touch</a>, and I’ve also played around with the Amazon Fire Phone, Windows Phone, iPod Touch… You get the idea.</p>
<p>Recently though, I’ve found the mobile landscape a bit boring. Android and iOS are the two big players, and it’s been that way for nearly a decade. Firefox OS, Blackberry OS, Windows Phone, and other would-be contenders have long since bitten the dust.</p>
<p>That’s why I’m excited about KaiOS. It’s a platform that’s <a href="https://techcrunch.com/2018/02/26/kaios-a-feature-phone-platform-built-on-the-ashes-of-firefox-os-adds-facebook-twitter-and-google-apps/">growing surprisingly fast</a> and is actually based on Firefox OS (may it rest in peace). It’s especially popular in India, where it’s already <a href="https://officechai.com/startups/kaios/">the second-most popular mobile OS after Android</a>.</p>
<p>KaiOS can run regular websites, but it can also run “packaged” apps, ala Firefox OS. So how can an aspiring KaiOS developer get started?</p>
<h2>Step one: buying a development phone</h2>
<p>I like to test on real devices, because I want to experience my app with real-world hardware and performance constraints, as an actual user would. I decided to get the <a href="https://www.nokia.com/phones/en_int/nokia-8110-4g">Nokia 8110 4G</a> because it was available on Amazon for $70.</p>
<p>Note that this phone only supports AT&amp;T in the U.S., so if you plan on using it as your actual personal phone, you may be out of luck.</p>
<p>When you first unbox the phone, you’ll have about 5 minutes’ worth of setup screens, after which you’re ready to go. I’d also recommend going into the settings and upgrading the OS, since mine needed an upgrade right away.</p>
<h2>Next steps: development environment</h2>
<p>The best resources I’ve found for KaiOS development are <a href="https://developer.kaiostech.com">the official developer guide</a> and <a href="https://paul.kinlan.me/debugging-web-pages-on-the-nokia-8110-with-kaios/">Paul Kinlan’s quick start guide</a>. Paul’s guide is the best place to start, since it’s short and will get you up and running quickly.</p>
<p>Paul says that he could only get <a href="https://developer.mozilla.org/en-US/docs/Archive/WebIDE">WebIDE</a> to work in Firefox 48, but I found that Firefox 59 also worked (per the KaiOS developer guide). So let’s use that.</p>
<p>First you’ll want to download Firefox 59 for your OS (in my case, Ubuntu) via <a href="https://ftp.mozilla.org/pub/firefox/releases/">Mozilla’s download site</a>. Sadly I could not get Firefox 59 to run alongside the latest Firefox (which is my go-to browser), and I also found that Firefox 59 tried to aggressively update itself, so every time I reopened it, it would be running the latest version. To work around that, you can run this script:</p>
<div><div class="syntaxhighlighter bash" id="highlighter_645392"><table border="0" cellpadding="0" cellspacing="0"><tbody><tr><td class="gutter"><div class="line number1 index0 alt2">1</div><div class="line number2 index1 alt1">2</div><div class="line number3 index2 alt2">3</div><div class="line number4 index3 alt1">4</div></td><td class="code"><div class="container"><div class="line number1 index0 alt2"><code class="bash functions">rm</code> <code class="bash plain">-fr firefox profile</code></div><div class="line number2 index1 alt1"><code class="bash functions">mkdir</code> <code class="bash plain">profile</code></div><div class="line number3 index2 alt2"><code class="bash functions">tar</code> <code class="bash plain">-xjf firefox-59.0.3.</code><code class="bash functions">tar</code><code class="bash plain">.bz2</code></div><div class="line number4 index3 alt1"><code class="bash plain">.</code><code class="bash plain">/firefox/firefox-bin</code> <code class="bash plain">-profile profile</code></div></div></td></tr></tbody></table></div></div>

<div><div class="syntaxhighlighter plain" id="highlighter_670017"><table border="0" cellpadding="0" cellspacing="0"><tbody><tr><td class="gutter"><div class="line number1 index0 alt2">1</div><div class="line number2 index1 alt1">2</div></td><td class="code"><div class="container"><div class="line number1 index0 alt2"><code class="plain plain">List of devices attached</code></div><div class="line number2 index1 alt1"><code class="plain plain">4939400 device</code></div></div></td></tr></tbody></table></div></div>
<p>If <code>adb</code> isn’t running, you can run <code>adb kill-server &amp;&amp; adb start-server</code> to restart it.</p>
<p>This didn’t work for me out of the box – I got an error saying it couldn’t connect to my device due to faulty <code>udev</code> rules. Luckily the KaiOS developer guide has a <a href="https://developer.kaiostech.com/getting-started/env-setup/os-env-setup">“Setting USB access”</a> script that will fix that.</p>
<p>After running that script, I used Paul’s trick of setting up <code>adb</code> forwarding:</p>

<h2>Next steps: actually writing code</h2>
<p>As far as I can tell, KaiOS is based on Firefox 48. You can tell by the user agent string:</p>
<div><div class="syntaxhighlighter plain" id="highlighter_833040"><table border="0" cellpadding="0" cellspacing="0"><tbody><tr><td class="gutter"><div class="line number1 index0 alt2">1</div></td><td class="code"><div class="container"><div class="line number1 index0 alt2"><code class="plain plain">Mozilla/5.0 (Mobile; Nokia_8110_4G; rv:48.0) Gecko/48.0 Firefox/48.0 KAIOS/2.5.1</code></div></div></td></tr></tbody></table></div></div>
<p>This means that you won’t necessarily have all the latest-and-greatest JavaScript or Web API features. Here’s a brief list of what I found didn’t work:</p>
<ul>
<li><code>async</code> functions</li>
<li><code>ServiceWorker</code></li>
<li><code>Intl</code></li>
</ul>
<p><em><strong>Update:</strong> it turns out ServiceWorker is supported! But you have to enable <a href="https://developer.kaiostech.com/api/clients">a permission in the manifest</a>. Thanks, <a href="https://mamot.fr/@fabricedesre/102846051602510560">Fabrice</a>!</em></p>
<p>As a quick gut-check of whether your app will run on KaiOS, you can try downloading Firefox 48, loading your website, and seeing if it works. (I found this easier than trying to debug on KaiOS right out of the gate.) You can use the same script above to run Firefox 48 with a fresh profile.</p>
<p>Once your code is sufficiently backwards-compatible (I found that <a href="https://babeljs.io/docs/en/babel-preset-env"><code>@babel/preset-env</code></a> with the default settings plus an <a href="https://www.npmjs.com/package/intl"><code>Intl</code> polyfill</a> was good enough for me as a starting point), you have two options for testing your app:</p>
<ul>
<li>as a packaged app</li>
<li>as a hosted app</li>
</ul>
<p>(If you’ve done Firefox OS development before, you’ll find these options familiar.)</p>
<p>I tried both techniques, but found that the hosted app was easier for quick testing. If your development machine and phone are on the same WiFi network, then you can create a <code>manifest.webapp</code> file per KaiOS’s documentation and then load a URL like so:</p>

<p>You can also try the packaged-app route, but I found that it didn’t play well with the routing library in my framework of choice (<a href="https://sapper.svelte.dev/">Sapper</a>) due to the extra <code>/index.html</code>. Plus, if I ever actually submit this app to the KaiStore, I’ll probably go with the hosted route since it’s less maintenance work.</p>
<h2>Optimizing for KaiOS</h2>
<p>In terms of web development, there are a few good things to be aware of when developing for KaiOS, and in particular for the Nokia 8110 4G.</p>
<p>First off, the available screen size is 240×294 pixels, which you can check by using <code>window.innerWidth</code> in JavaScript, <code>@media (max-width: 240px)</code> in CSS, etc. If you set <code>"fullscreen": true</code> to hide the status bar, you can get slightly more breathing room: 240×320.</p>
<p>I had already optimized my app for the iPhone 4’s screen size (which is 320×480), but I found I had to do extra work to make things show up correctly on an even tinier screen.</p>
<div class="wp-caption aligncenter" data-shortcode="caption" id="attachment_8068" style="width: 580px"><a href="https://nolanwlawson.files.wordpress.com/2019/09/out.png"><img alt="Screenshot comparing Pinafore on an iPhone 4 versus a smaller Nokia 8110 4G" aria-describedby="caption-attachment-8068" class="size-large wp-image-8068" data-attachment-id="8068" data-comments-opened="1" data-image-description="" data-image-meta='{"aperture":"0","credit":"","camera":"","caption":"","created_timestamp":"0","copyright":"","focal_length":"0","iso":"0","shutter_speed":"0","title":"","orientation":"0"}' data-image-title="out" data-large-file="https://nolanwlawson.files.wordpress.com/2019/09/out.png?w=570" data-medium-file="https://nolanwlawson.files.wordpress.com/2019/09/out.png?w=300" data-orig-file="https://nolanwlawson.files.wordpress.com/2019/09/out.png" data-orig-size="748,570" data-permalink="https://nolanlawson.com/2019/09/22/the-joy-and-challenge-of-developing-for-kaios/out-6/" height="434" sizes="(max-width: 570px) 100vw, 570px" src="https://nolanwlawson.files.wordpress.com/2019/09/out.png?w=570&amp;h=434" srcset="https://nolanwlawson.files.wordpress.com/2019/09/out.png?w=570&amp;h=434 570w, https://nolanwlawson.files.wordpress.com/2019/09/out.png?w=150&amp;h=114 150w, https://nolanwlawson.files.wordpress.com/2019/09/out.png?w=300&amp;h=229 300w, https://nolanwlawson.files.wordpress.com/2019/09/out.png 748w" width="570"/></a><p class="wp-caption-text" id="caption-attachment-8068">The iPhone 4 is already pretty small, but it’s a giant compared to the Nokia 8110 4G.</p></div>
<p>Next, the input methods are quite limited. If you’ve actually taken the time to make your webapp keyboard-accessible, then you should be most of the way there. But there are still some extra optimizations you may have to make for KaiOS.</p>
<p>By default, the <kbd>↑</kbd> and <kbd>↓</kbd> arrows will typically scroll the page up or down. I decided to use the <kbd>←</kbd> and <kbd>→</kbd> arrows to change the focus – i.e. to act as proxies for the <kbd>Tab</kbd> and <kbd>Shift</kbd> + <kbd>Tab</kbd> keys. I wrote some <a href="https://github.com/nolanlawson/pinafore/blob/f284ae8b7381b29556bcf62f4812c75802109762/src/routes/_utils/leftRightNavShortcuts.js">fairly simple logic</a> to navigate through the focusable elements on the page, taking special care to allow the arrow keys to work properly inside of text inputs and modal dialogs.</p>
<p>I also found that the focus outlines were a bit hard to see on the small screen, so I scaled them up for KaiOS and added some extra styling to make the focus more obvious.</p>
<p>Some apps may opt to display an onscreen cursor (this seems to be the default behavior of the web browser), but I found that to be a bit of a clumsy experience. So I think managing the focus is better.</p>

<h2>Other KaiOS web developer hurdles</h2>
<p>The next most difficult thing about KaiOS is still the lack of modern browser standards. For instance, I couldn’t get SVG <code>&lt;use&gt;</code> tags to work properly, so I fell back to inlining each SVG as a workaround.</p>
<p>CSS Grid is (mercifully) supported, so I didn’t have to backport my Grid logic. Since Grid is <a href="https://caniuse.com/#search=grid">not supported in Firefox 48</a>, this hints to me that KaiOS must have tweaked the Firefox OS code beyond what Firefox 48 can support. But I haven’t done the full rundown of all the supported features. (And I still find it helpful to use Firefox 48 as a minimum bar for a quick test target.)</p>
<p>As with all web development, this is the area where you’ll probably have to roll up your sleeves and test for what’s supported and what’s not. But overall I find KaiOS to be much easier to develop for than, say, IE11. It’s much further along on the standards track than a truly legacy browser.</p>
<p>Once you’ve gotten past those hurdles, though, the result can be surprisingly good! I was impressed at how well this tiny feature phone could run Pinafore:</p>

<h2>Conclusion</h2>
<p>Building for KaiOS is fun! The device is quirky and lightweight, and it makes me excited about mobile development in a way that I haven’t felt in a while. In terms of development, it feels like a nice compromise between a feature phone with limited hardware (small screen, no touch, limited key input) and a smartphone OS with cutting-edge web technologies (it has CSS Grid! And <code>String.prototype.padStart()</code>! It’s not so bad!).</p>
<p>However, I’m not a huge fan of app stores – I don’t like having to agree to the <abbr title="Terms of Service">ToS</abbr>, going through a review process, and ultimately subjecting myself to the whims of a private corporation. But KaiOS is neat, it’s cute, and it’s growing in developing markets, so I think it’s a worthy venue for development.</p>
<p>And unlike fully proprietary development platforms, you’re not writing throwaway code if KaiOS ever goes away. Since it’s ultimately just a webapp, improvements I’ve made to Pinafore for keyboard accessibility and small screens will accrue to any other device that can browse the web. Other than the <code>manifest.webapp</code> file, there’s nothing truly specific to KaiOS that I had to do to support it.</p>
<p>Overall, I find it fun and refreshing to build for something like KaiOS. It helps me see the web platform from a new perspective, and if nothing else, I’ve got a new gadget to play with.</p>

<h2><a href="https://nolanlawson.com/2019/08/14/browsers-input-events-and-frame-throttling/" rel="bookmark">Browsers, input events, and frame throttling</a></h2>
<p class="metadata">
	Posted by Nolan Lawson in <a href="https://nolanlawson.com/tag/performance/" rel="category tag">performance</a>, <a href="https://nolanlawson.com/category/web/" rel="category tag">Web</a>.		<span class="feedback"><a href="https://nolanlawson.com/2019/08/14/browsers-input-events-and-frame-throttling/#comments">1 Comment</a></span></p>
<div class="entry">
<p>If there’s one thing I’ve learned about web performance, it’s that you have to approach it with a sense of open-mindedness and humility. Otherwise, prepare to be humbled.</p>
<p>Just as soon as you think you’ve got it all figured out, poof! Browsers change their implementation. Or poof! The spec changes. Or poof! You just flat-out turn out to be wrong. So you have to constantly test and revalidate your assumptions.</p>
<p>In <a href="https://nolanlawson.com/2019/08/11/high-performance-input-handling-on-the-web/">a recent post</a>, I suggested that <code>pointermove</code> events fire more frequently than <code>requestAnimationFrame</code>, and so it’s a good idea to throttle them to <code>rAF</code>. I also rattled off some other events that may fire faster than <code>rAF</code>, such as <code>scroll</code>, <code>wheel</code>, <code>touchmove</code>, and <code>mousemove</code>.</p>
<p>Do these events actually fire faster than <code>rAF</code>, though? It’s an important detail! If browsers already align/throttle these events to <code>rAF</code>, then there’s little point in recreating that same behavior in userland. (Thankfully an extra <code>rAF</code> won’t add an extra frame delay, though, assuming browsers fire the <code>rAF</code>-aligned events right before <code>rAF</code>. Thanks <a href="https://jakearchibald.com/">Jake Archibald</a> for this tip!)</p>
<p><em><strong>TL;DR:</strong> it varies across browsers and events. I’d still recommend the <a href="https://nolanlawson.com/2019/08/11/high-performance-input-handling-on-the-web/"><code>rAF</code>-throttling technique</a> described in my previous post.</em></p>
<h2>Step one: check the spec</h2>
<p>The first question to ask is: what does the spec say?</p>
<p>After reading the specs for <code>pointermove</code>, <code>mousemove</code>, <code>touchmove</code>, <code>scroll</code>, and <code>wheel</code>, I found that the only mention of animation frame timing was in <code>pointermove</code> and <code>scroll</code>. The spec for <code>pointermove</code> <a href="https://w3c.github.io/pointerevents/extension.html#the-pointermove-event">says</a>:</p>
<blockquote><p>
  A user agent MUST fire a pointer event named <code>pointermove</code> when a pointer changes button state. […] These events <strong>may</strong> be coalesced or aligned to animation frame callbacks based on UA decision.
</p></blockquote>
<p>(Emphasis mine.) So browsers are not required to coalesce or align <code>pointermove</code> events to animation frames, but they may do so. (Presumably, this is the point of <a href="https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent/getCoalescedEvents"><code>getCoalescedEvents()</code></a>.)</p>
<p>As for <code>scroll</code>, it’s mentioned <a href="https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model">in the event loop spec</a>, where it says “for each fully active Document […], run the <code>scroll</code> steps for that Document” as part of the steps before running <code>rAF</code> callbacks. So on the main <code>document</code> at least, <code>scroll</code> is definitely supposed to fire before <code>rAF</code>.</p>
<p>For contrast, <a href="https://w3c.github.io/touch-events/#the-touchmove-event">here’s <code>touchmove</code></a>:</p>
<blockquote><p>
  A user agent must dispatch this event type to indicate when the user moves a touch point along the touch surface. […] <strong>Note that the rate at which the user agent sends touchmove events is implementation-defined</strong>, and may depend on hardware capabilities and other implementation details.
</p></blockquote>
<p>(Emphasis mine.) So this time, nothing about animation frames, and also some language about “implementation-defined.” Similarly, <a href="https://w3c.github.io/uievents/#event-type-mousemove">here’s <code>mousemove</code></a>:</p>
<blockquote><p>
<strong>The frequency rate of events while the pointing device is moved is implementation-, device-, and platform-specific</strong>, but multiple consecutive mousemove events SHOULD be fired for sustained pointer-device movement, rather than a single event for each instance of mouse movement.
</p></blockquote>
<p>(Emphasis mine.) So we’re starting to get a pretty clear picture (or a hazy one, depending on your perspective). It seems that, aside from <code>scroll</code>, the specs don’t have much to say about whether events should be coalesced with <code>rAF</code> or not.</p>
<h2>Step two: test it</h2>
<p>However, this doesn’t mean browsers don’t do it! After all, it’s clearly in browsers’ interests to coalesce these events to animation frames. Assuming that most web developers do the simplest possible thing and handle the events directly, then any browser that aligns with <code>rAF</code> will avoid some unintentional jank from noisy input events.</p>
<p>Do browsers actually do this, though? Thankfully Jake has written <a href="https://event-timing.glitch.me">a nice demo</a> which makes it easy to test this. I’ve also <a href="https://event-timing-with-scroll.glitch.me/">extended his demo</a> to test <code>scroll</code> events. <h2>Conclusion</h2>
<p>As you can see from the data, there is a lot of variance in terms of which events and browsers align to <code>rAF</code>. Although for the most part, it seems consistent within browser engines (e.g. GNOME Web is a WebKit-based browser, and it patterns with macOS Safari). Note though that I only tested a regular mouse or trackpad, not exotic input devices such as a <a href="https://nolanlawson.com/2019/08/11/high-performance-input-handling-on-the-web/#comment-116168">Wacom stylus</a>, Surface Pen, etc.</p>
<p>Given this data, I would take the cautious approach and still do the manual <code>rAF</code>-throttling as described in my previous blog post. It has the upside of being guaranteed to work roughly the same across all browsers, at the cost of some extra bookkeeping. <a href="#footnote-1"><sup>[1]</sup></a></p>
<p>Depending on your supported browser matrix, though, and depending on when you’re reading this (maybe at a point in the future when all browser input events are <code>rAF</code>-aligned!), then you may just handle the input directly and trust the browser to align it to <code>rAF</code>. <a href="#footnote-2"><sup>[2]</sup></a></p>
<p><em>Thanks to Ben Kelly and Jake Archibald for feedback on a draft of this blog post. Thanks also to Jake for <a href="https://nolanlawson.com/2019/08/11/high-performance-input-handling-on-the-web/#comment-116142">clueing me in</a> to this <code>rAF</code>-throttling business in the first place.</em></p>
<h2>Footnotes</h2>
<p><a name="footnote-1"></a>1. Interestingly, in the case of <code>pointermove</code> at least, the browser behavior can be feature-detected by checking <a href="https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent/getCoalescedEvents"><code>getCoalescedEvents</code></a> (i.e. Firefox and Chrome have it, Edge and Safari Technology Preview don’t). So you can use <code>PointerEvent.prototype.getCoalescedEvents</code> as a feature check. But there’s little point in feature-detecting, since manual <code>rAF</code>-throttling doesn’t add an extra frame delay in browsers that already <code>rAF</code>-align.</p>
<p><a name="footnote-2"></a>2. Jake also pointed me to an interesting detail: “Although these events are synced to rendering, they’ll flush if another non-synced event happens.” So for instance, keyboard events will interfere with <code>pointermove</code> and cause them to no longer sync to <code>rAF</code>, which you can reproduce in <a href="https://event-timing.glitch.me/">Jake’s demo</a> by typing on the keyboard and moving the mouse at the same time. Another good reason to just <code>rAF</code>-throttle and be sure!</p>

<h2><a href="https://nolanlawson.com/2019/08/11/high-performance-input-handling-on-the-web/" rel="bookmark">High-performance input handling on the web</a></h2>
<p class="metadata">
	Posted by Nolan Lawson in <a href="https://nolanlawson.com/tag/performance/" rel="category tag">performance</a>, <a href="https://nolanlawson.com/category/web/" rel="category tag">Web</a>.		<span class="feedback"><a href="https://nolanlawson.com/2019/08/11/high-performance-input-handling-on-the-web/#comments">16 Comments</a></span></p>
<div class="entry">
<p><em><strong>Update:</strong> In a <a href="https://nolanlawson.com/2019/08/14/browsers-input-events-and-frame-throttling/">follow-up post</a>, I explore some of the subtleties across browsers in how they fire input events.</em></p>
<p>There is a class of UI performance problems that arise from the following situation: <em>An input event is firing faster than the browser can paint frames.</em></p>
<p>Several events can fit this description:</p>
<ul>
<li><code>scroll</code></li>
<li><code>wheel</code></li>
<li><code>mousemove</code></li>
<li><code>touchmove</code></li>
<li><code>pointermove</code></li>
<li>etc.</li>
</ul>
<p>Intuitively, it makes sense why this would happen. A user can jiggle their mouse and deliver precise x/y updates faster than the browser can paint frames, especially if the UI thread is busy and thus the framerate is being throttled (also known as “jank”).</p>
<p><a href="https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-12-52-15-1.png"><img alt="Screenshot of Chrome Dev Tools showing that a long frame of 546ms can contain as many as four pointermove events" class="aligncenter size-large wp-image-7738" data-attachment-id="7738" data-comments-opened="1" data-image-description="" data-image-meta='{"aperture":"0","credit":"","camera":"","caption":"","created_timestamp":"0","copyright":"","focal_length":"0","iso":"0","shutter_speed":"0","title":"","orientation":"0"}' data-image-title="Screenshot from 2019-08-10 12-52-15" data-large-file="https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-12-52-15-1.png?w=570" data-medium-file="https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-12-52-15-1.png?w=300" data-orig-file="https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-12-52-15-1.png" data-orig-size="866,393" data-permalink="https://nolanlawson.com/2019/08/11/high-performance-input-handling-on-the-web/screenshot-from-2019-08-10-12-52-15-2/" height="259" sizes="(max-width: 570px) 100vw, 570px" src="https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-12-52-15-1.png?w=570&amp;h=259" srcset="https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-12-52-15-1.png?w=570&amp;h=259 570w, https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-12-52-15-1.png?w=150&amp;h=68 150w, https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-12-52-15-1.png?w=300&amp;h=136 300w, https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-12-52-15-1.png?w=768&amp;h=349 768w, https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-12-52-15-1.png 866w" width="570"/></a></p>
<p>In the above screenshot, <code>pointermove</code> events are firing faster than the framerate can keep up.<a href="#footnote-1"><sup>[1]</sup></a> This can also happen for scroll events, touch events, etc.</p>
<p><em><strong>Update:</strong> In Chrome, <code>pointermove</code> is actually supposed to <a href="https://nolanlawson.com/2019/08/11/high-performance-input-handling-on-the-web/#comment-116142">align/throttle to <code>requestAnimationFrame</code> automatically</a>, but there is a bug where it <a href="https://bugs.chromium.org/p/chromium/issues/detail?id=992954">behaves differently with Dev Tools open</a>.</em></p>
<p>The performance problem occurs when the developer naïvely chooses to handle the input directly:</p>
<div><div class="syntaxhighlighter jscript" id="highlighter_235293"><table border="0" cellpadding="0" cellspacing="0"><tbody><tr><td class="gutter"><div class="line number1 index0 alt2">1</div><div class="line number2 index1 alt1">2</div><div class="line number3 index2 alt2">3</div></td><td class="code"><div class="container"><div class="line number1 index0 alt2"><code class="jscript plain">element.addEventListener(</code><code class="jscript string">'pointermove'</code><code class="jscript plain">, () =&gt; {</code></div><div class="line number2 index1 alt1"><code class="jscript spaces">  </code><code class="jscript plain">doExpensiveOperation()</code></div><div class="line number3 index2 alt2"><code class="jscript plain">})</code></div></div></td></tr></tbody></table></div></div>
<p>In <a href="https://nolanlawson.com/2018/09/01/a-tour-of-javascript-timers-on-the-web/">a previous post</a>, I discussed Lodash’s <a href="https://lodash.com/docs/4.17.15#debounce">debounce</a> and <a href="https://lodash.com/docs/4.17.15#throttle">throttle</a> functions, which I find very useful for these kinds of situations. Recently however, I found a pattern I like even better, so I want to discuss that here.</p>
<h2>Understanding the event loop</h2>
<p>Let’s take a step back. What exactly are we trying to achieve here? Well, we want the browser to do only the work necessary to paint the frames that it’s able to paint. For instance, in the case of a <code>pointermove</code> event, we may want to update the x/y coordinates of an element rendered to the DOM.</p>
<p>The problem with Lodash’s <code>throttle()</code>/<code>debounce()</code> is that we would have to choose an arbitrary delay (e.g. 20 milliseconds or 50 milliseconds), which may end up being faster or slower than the browser is actually able to paint, depending on the device and browser. So really, we want to throttle to <code>requestAnimationFrame()</code>:</p>
<div><div class="syntaxhighlighter jscript" id="highlighter_855226"><table border="0" cellpadding="0" cellspacing="0"><tbody><tr><td class="gutter"><div class="line number1 index0 alt2">1</div><div class="line number2 index1 alt1">2</div><div class="line number3 index2 alt2">3</div></td><td class="code"><div class="container"><div class="line number1 index0 alt2"><code class="jscript plain">element.addEventListener(</code><code class="jscript string">'pointermove'</code><code class="jscript plain">, () =&gt; {</code></div><div class="line number2 index1 alt1"><code class="jscript spaces">  </code><code class="jscript plain">requestAnimationFrame(doExpensiveOperation)</code></div><div class="line number3 index2 alt2"><code class="jscript plain">})</code></div></div></td></tr></tbody></table></div></div>
<p>With the above code, we are at least aligning our work with the browser’s event loop, i.e. firing right before style and layout are calculated.</p>
<p>However, even this is not really ideal. Imagine that a <code>pointermove</code> event fires three times for every frame. In that case, we will essentially do three times the necessary work on every frame:</p>
<p><a href="https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-13-08-55.png"><img alt="Chrome Dev Tools screenshot showing an 82 millisecond frame where there are three pointermove events queued by requestAnimationFrame inside of the frame" class="aligncenter size-full wp-image-7746" data-attachment-id="7746" data-comments-opened="1" data-image-description="" data-image-meta='{"aperture":"0","credit":"","camera":"","caption":"","created_timestamp":"0","copyright":"","focal_length":"0","iso":"0","shutter_speed":"0","title":"","orientation":"0"}' data-image-title="Screenshot from 2019-08-10 13-08-55" data-large-file="https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-13-08-55.png?w=505" data-medium-file="https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-13-08-55.png?w=300" data-orig-file="https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-13-08-55.png" data-orig-size="505,261" data-permalink="https://nolanlawson.com/2019/08/11/high-performance-input-handling-on-the-web/screenshot-from-2019-08-10-13-08-55/" sizes="(max-width: 505px) 100vw, 505px" src="https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-13-08-55.png?w=570" srcset="https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-13-08-55.png 505w, https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-13-08-55.png?w=150 150w, https://nolanwlawson.files.wordpress.com/2019/08/screenshot-from-2019-08-10-13-08-55.png?w=300 300w"/></a></p>
<p>This may be harmless if the code is fast enough, or if it’s only writing to the DOM. However, if it’s both <em>writing to</em> and <em>reading from</em> the DOM, then we will end up with the classic <a href="https://developers.google.com/web/fundamentals/performance/rendering/avoid-large-complex-layouts-and-layout-thrashing">layout thrashing</a> scenario,<a href="#footnote-2"><sup>[2]</sup></a> and our <code>rAF</code>-based solution is actually no better than handling the input directly, because we recalculate the style and layout for every <code>pointermove</code> event.</p>

<h2>Throttling based on framerate</h2>
<p>Again, let’s take a step back and figure out what we’re trying to do. If the user is dragging their finger across the screen, and <code>pointermove</code> fires 3 times for every frame, then we actually don’t care about the first and second events. We only care about the third one, because that’s the one we need to paint.</p>
<p>So let’s only run the <em>final</em> callback before each <code>requestAnimationFrame</code>. This pattern will work nicely:</p>
<div><div class="syntaxhighlighter jscript" id="highlighter_803704"><table border="0" cellpadding="0" cellspacing="0"><tbody><tr><td class="gutter"><div class="line number1 index0 alt2">1</div><div class="line number2 index1 alt1">2</div><div class="line number3 index2 alt2">3</div><div class="line number4 index3 alt1">4</div><div class="line number5 index4 alt2">5</div><div class="line number6 index5 alt1">6</div><div class="line number7 index6 alt2">7</div><div class="line number8 index7 alt1">8</div><div class="line number9 index8 alt2">9</div><div class="line number10 index9 alt1">10</div><div class="line number11 index10 alt2">11</div><div class="line number12 index11 alt1">12</div><div class="line number13 index12 alt2">13</div></td><td class="code"><div class="container"><div class="line number1 index0 alt2"><code class="jscript keyword">function</code> <code class="jscript plain">throttleRAF () {</code></div><div class="line number2 index1 alt1"><code class="jscript spaces">  </code><code class="jscript keyword">let</code> <code class="jscript plain">queuedCallback</code></div><div class="line number3 index2 alt2"><code class="jscript spaces">  </code><code class="jscript keyword">return</code> <code class="jscript plain">callback =&gt; <p>We could also use <a href="https://developer.mozilla.org/en-US/docs/Web/API/Window/cancelAnimationFrame">cancelAnimationFrame</a> for this, but I prefer the above solution because it’s calling fewer DOM APIs. (It only calls <code>requestAnimationFrame()</code> once per frame.)</p>
<p>This is nice, but at this point we can still optimize it further. Recall that we want to avoid layout thrashing, which means we want to batch all of our reads and writes to avoid unnecessary recalculations.</p>
<p>In <a href="https://nolanwlawson.wordpress.com/2018/09/25/accurately-measuring-layout-on-the-web/">“Accurately measuring layout on the web”</a>, I explore some patterns for queuing a timer to fire <em>after</em> style and layout are calculated. Since writing that post, a new web standard called <a href="https://github.com/WICG/requestPostAnimationFrame">requestPostAnimationFrame</a> has been proposed, and it fits the bill nicely. There is also a good polyfill called <a href="https://github.com/andrewiggins/afterframe">afterframe</a>.</p>
<p>To best align our DOM updates with the browser’s event loop, we want to follow these simple rules:</p>
<ol>
<li>DOM writes go in <code>requestAnimationFrame()</code>.</li>
<li>DOM reads go in <code>requestPostAnimationFrame()</code>.</li>
</ol>
<p>The reason this works is because we write to the DOM right before the browser will need to calculate style and layout (in <code>rAF</code>), and then we read from the DOM once the calculations have been made and the DOM is “clean” (in <code>rPAF</code>).</p>
<p>If we do this correctly, then we shouldn’t see any warnings in the Chrome Dev Tools about “forced reflow” (i.e. a forced style/layout outside of the browser’s normal event loop). Instead, all layout calculations should happen during the regular event loop cycle.</p>

<p>To accomplish this, let’s make our throttler more generic, and create one that can handle <code>requestPostAnimationFrame</code> as well:</p>

<h2>Pointer event pitfalls</h2>
<p>The last piece of the puzzle (at least for me, while implementing a UI like this), was to avoid the <a href="https://github.com/wessberg/pointer-events#readme">pointer events polyfill</a>. I found that, even after implementing all the above performance improvements, my UI was still janky in Firefox for Android.</p>
<p>After some digging with <a href="https://developer.mozilla.org/en-US/docs/Archive/WebIDE">WebIDE</a>, I found that <a href="https://caniuse.com/#feat=pointer">Firefox for Android currently does not support Pointer Events</a>, and instead only supports Touch Events. (This is similar to the current version of iOS Safari.) After profiling, I found that the polyfill itself was taking up a lot of my frame budget.</p>

Hopefully in the near future this won’t be necessary, and all browsers will support Pointer Events! <a href="https://caniuse.com/#feat=pointer">We’re already close</a>.</p>

<p> </p>
<p>When handling very performance-sensitive scenarios, like a UI that should respond to every <code>pointermove</code> event, it’s important to reduce the amount of work done on each frame. I’m sure that this polyfill is useful in other situations, but in my case, it was just adding too much overhead.</p>
<p>One other optimization I made was to delay updates to the store (which trigger some extra JavaScript computations) until the user’s drag had completed, instead of on every drag event. The end result is that, even on a resource-constrained device like the Nexus 5, the UI can actually keep up with the user’s finger!</p>
<h2>Conclusion</h2>
<p>I hope this blog post was helpful for anyone handling <code>scroll</code>, <code>touchmove</code>, <code>pointermove</code>, or similar input events. Thinking in terms of how I’d like to align my work with the browser’s event loop (using <code>requestAnimationFrame</code> and <code>requestPostAnimationFrame</code>) was useful for me.</p>
<p>Note that I’m not saying to never use Lodash’s <code>throttle</code> or <code>debounce</code>. I use them all the time! Sometimes it makes sense to just let a timer fire every <em>n</em> milliseconds – e.g. when debouncing window <code>resize</code> events. In other cases, I like using <code>requestIdleCallback</code> – for instance, when updating a non-critical part of the UI based on user input, like a “number of characters remaining” counter when typing into a text box.</p>
<p>In general, though, I hope that once <code>requestPostAnimationFrame</code> makes its way into browsers, web developers will start to think more purposefully about how they do UI updates, leading to fewer instances of layout thrashing. <a href="https://github.com/wilsonpage/fastdom">fastdom</a> was written in 2013, and yet its lessons still apply today. Hopefully when <code>rPAF</code> lands, it will be much easier to use this pattern and reduce the impact of layout thrashing on web performance.</p>
<h2>Footnotes</h2>
<p><a name="footnote-1"></a>1. In the <a href="https://w3c.github.io/pointerevents/extension.html#the-pointermove-event">Pointer Events Level 2 spec</a>, it says that <code>pointermove</code> events “may be coalesced or aligned to animation frame callbacks based on UA decision.” So hypothetically, a browser could throttle <code>pointermove</code> to fire only once per <code>rAF</code> (and if you need precise x/y events, e.g. for a drawing app, you can use <code>getCoalescedEvents()</code>). <strike>It’s not clear to me, though, that any browser actually does this.</strike> <em><strong>Update:</strong> see comments below, some browsers do!</em> In any case, throttling the events to <code>rAF</code> in JavaScript accomplishes the same thing, regardless of UA behavior.</p>
<p><a name="footnote-2"></a>2. Technically, the only DOM reads that matter in the case of layout thrashing are <a href="https://gist.github.com/paulirish/5d52fb081b3570c81e3a">DOM APIs that force style/layout</a>, e.g. <code>getBoundingClientRect()</code> and <code>offsetLeft</code>. If you’re just calling <code>getAttribute()</code> or <code>classList.contains()</code>, then you’re not going to trigger style/layout recalculations.</p>
<p><a name="footnote-3"></a>3. Note that if you have different parts of the code that are doing separate reads/writes, then each one will need its own throttler function. Otherwise one throttler could cancel the other one out. This can be a bit tricky to get right, although to be fair the same footgun exists with Lodash’s <code>debounce</code>/<code>throttle</code>.</p>

<h2><a href="https://nolanlawson.com/2019/06/17/advice-for-new-bicycle-commuters/" rel="bookmark">Advice for new bicycle commuters</a></h2>
<p class="metadata">
	Posted by Nolan Lawson in <a href="https://nolanlawson.com/category/bicycling/" rel="category tag">Bicycling</a>.		<span class="feedback"><a href="https://nolanlawson.com/2019/06/17/advice-for-new-bicycle-commuters/#comments">7 Comments</a></span></p>
<div class="entry">

<p>I started biking to work last summer, around 8-10 miles per day. Overall it’s been a big boon to my health – I’ve lost weight, I feel happier, and I have a new hobby to geek out over. But there are some lessons I wish I had learned earlier, so in this post I’m going to offer some advice to new cyclists.</p>
<p>Note: I’m not a doctor, a physical therapist, or even a big expert on cycling. So take my advice with a grain of salt.</p>
<h2>Gear</h2>
<p>You don’t need a lot of expensive gear to be a bike commuter. I used a 20-year-old hand-me-down mountain bike for my first few months, before I decided I was serious enough to want an upgrade.</p>
<p>The most important thing is safety: flashing lights, bright colors. If you’re going to be biking alongside traffic, you want to be visible in all conditions: daytime, nighttime, dusk, etc. If you don’t have a brightly-colored backpack, get a <a href="https://www.amazon.com/gp/product/B017R9OR8C/">backpack cover</a> that’s bright yellow with reflective strips. As a bonus, it will keep your backpack dry.</p>
<p>The second most important thing is comfort. I really like the <a href="https://dilbert.com/strip/1994-07-18">dorky bike shorts</a> with padding on bottom, because they reduce saddle sores, but you can also just use regular gym shorts. You don’t need special bike shoes, but you may want to use a different pair than you wear throughout the day, because they will get sweaty and stinky. In the winter, make sure to have gloves, a scarf, and a hat that will fit under your helmet.</p>
<h2>Safety</h2>
<p>I’ll say it again: flashing lights, bright colors. Some cars will treat you with respect, but a lot of drivers are just distracted or lazy and won’t see you coming. Deck yourself out like the yellow Power Ranger, and even then don’t assume that cars will see you.</p>
<p>Traditionally there are <a href="https://en.wikipedia.org/wiki/Hand_signals">hand sigals</a> for left turns and right turns. I don’t use the “bent elbow” left-hand signal for right turns, because I assume that no driver has seen that signal since the 1930’s. You’re better off just pointing with your right hand.</p>
<p>If you’re on a road without a bike lane, or if there’s barely any shoulder, then try to make it clear that you don’t want to be passed. Otherwise if you keep too far to the right, then drivers will take it as an invitation to pass you, even if you’re just inches away from their side mirror. Drive in the middle of the lane if you have to. Better to slow down someone’s commute than to be roadkill.</p>
<p>Look behind you when you merge left. Practice it if it’s hard to ride a straight line while doing so. I prefer this to using a rearview mirror, because it makes it really obvious to drivers that I’m craning my neck and so they should watch my movement.</p>
<p>If you can alter your route to include more dedicated bike paths and bike trails, then do it. Adding a few extra minutes to your commute is worth the peace of mind. Plus, you’re trying to get some exercise, right?</p>

<h2>Health</h2>
<p>Biking has a lot of health hazards, but I’m just going to talk about the ones that affected me.</p>
<p>If you get <a href="https://en.wikipedia.org/wiki/Bicycle_handlebar#Drop">drop bars</a>, make sure you’re using them correctly. I made the mistake of over-using the lower position (“I’m going so fast! I’m a real cyclist now!”), and it really did a number on my wrists. I ended up with a lot of chronic wrist pain until I learned to do it right. It’s better now, but I can’t do push-ups anymore.</p>
<p>Basic advice: use the middle “Atari joystick” position for 90% of your ride, use the upper position on uphills (to lean back and get bigger lungfuls of air), and only use the lower position on downhills, when you want more control over your brakes and a bit more speed. Try to work your core muscles so you’re not putting weight on your wrists, and switch up your position occasionally.</p>
<p>Get a <a href="https://www.rei.com/learn/expert-advice/bike-fit.html">bike fitting</a>. Yes, it can be expensive (mine ran $150), but it’s way cheaper than physical therapy. They’ll adjust your saddle height, your handlebar position, and everything else for maximum comfort. This can prevent all sorts of back and wrist pain. I wish I had done it earlier.</p>
<h2>Have fun</h2>
<p>Keep at it. Drink lots of water. Don’t feel bad when you get passed by 60 year-old dudes with gray beards – instead, think about how someday <em>you</em> could be that silverfox!</p>
<p>The other cyclists you see on the road are, statistically speaking, likely to be more hardcore than you. They probably spend a lot more time cycling – hence why you see them. So don’t feel bad about getting passed.</p>
<p>If there’s a particularly nasty uphill on your route, just think to yourself, “It gets a little easier every day.” Because the truth is, it does! Pretty soon you’ll be shaving time off your commute, and you may even find that it’s faster than other modes of transportation. (For me, cycling actually beats the bus, especially in bad traffic.)</p>
<p>So that’s it for my newbie cycling advice. Cycling is fun, it’s good for your health, and it’s good for the environment. Plus, the more you normalize it, the more you encourage other people to brave the car traffic and try cycling.</p>

<li><a href="#the-last-unicorn-by-peter-s">The Last Unicorn by Peter S. Beagle</a></li>
<li><a href="#the-magicians-trilogy-by-lev">The Magicians Trilogy by Lev Grossman</a></li>
<li><a href="#on-the-beach-by-nevil">On the Beach by Nevil Shute</a></li>
<li><a href="#radicalized-by-cory">Radicalized by Cory Doctorow</a></li>
</ul>
<h3>Non-fiction</h3>
<ul>
<li><a href="#eating-animals-by-jonathan">Eating Animals by Jonathan Safran Foer</a></li>
<li><a href="#the-uninhabitable-earth-life">The Uninhabitable Earth: Life After Warming by David Wallace-Wells</a></li>
<li><a href="#the-sixth-extinction-by">The Sixth Extinction by Elizabeth Kolbert</a></li>
</ul>
<h2>Fiction</h2>
<h3><a href="https://www.goodreads.com/book/show/8890606-the-last-unicorn">The Last Unicorn by Peter S. Beagle</a><a name="the-last-unicorn-by-peter-s"></a></h3>
<p>A haunting, beautiful book. I’d never considered myself a big fantasy fan, but somehow this one really stuck with me. I decided to read it because of <a href="https://www.theatlantic.com/entertainment/archive/2018/11/last-unicorn-peter-beagle-50th-anniversary-reality-magic/575641/">this Atlantic article</a>, and I’m glad I did.</p>
<p>I think what sets this one apart is that, while books like <em>Harry Potter</em> or the <em>Narnia</em> series are about childhood and its relationship with fantasy, <em>The Last Unicorn</em> is about growing up and growing <em>away</em> from fantasy. In the book, people have forgotten about unicorns or can’t see their horns. Some of them look upon the unicorn and start crying even if they don’t know why.</p>
<p>The book is ultimately about loss – loss of childhood, loss of innocence, loss of childish fantasies – as well as regret. It’s a very profound and moving book. Oh, and the author has a real gift for language; the book is filled with beautiful poetry to paint its fantasy world. Anyway, read it.</p>
<h3><a href="https://www.goodreads.com/book/show/6101718-the-magicians">The Magicians Trilogy by Lev Grossman</a><a name="the-magicians-trilogy-by-lev"></a></h3>
<p>I decided after reading <em>The Last Unicorn</em> that I should start taking fantasy books a bit more seriously. So I picked up <em>The Magicians</em>, and quickly devoured all three books in the trilogy. The whole series is great, although for slightly different reasons than <em>Unicorn</em>.</p>
<p>At first glance, <em>Magicians</em> comes across as a mash-up between <em>Harry Potter</em> and <em>Narnia</em>, but with some decidedly adult elements thrown in. At times I burst out laughing at the incongruity between the magical situations that the characters found themselves in and their wry commentary on it. These are fantasy novels for people who think fantasy novels are a bit silly.</p>
<p>In the end, though, I think <em>Magicians</em> is actually closest in theme and tone to <em>The Dark Tower</em> by Stephen King. It has the same sense of taking old fables and tropes and turning them into something gritty and believable. It’s a fantasy world seen through a dark, ironic lens. But it’s also a great piece of storytelling. Well worth the read.</p>
<h3><a href="https://www.goodreads.com/book/show/38180.On_the_Beach">On the Beach by Nevil Shute</a><a name="on-the-beach-by-nevil"></a></h3>
<p>I needed one last piece of post-apocalyptic fiction for the road, before switching over to the wizards and unicorns.</p>
<p>This one tells a good story, although ultimately I don’t find its depiction of a world waiting to die very believable. I just find it hard to imagine that, in the face of a nuclear dust-cloud descending inexorably towards Australia, that an entire continent would decide to go the “stiff upper lip” route and carry on as usual, pretending as if Armageddon wasn’t on its way.</p>
<p>Societal breakdown and anarchy seem more likely to me, although I guess that might be hindsight talking. This book was written in 1957, well before post-apocalyptic fiction had really settled into its groove and the <em>Mad Max</em>-style mohawked warlords had become staples of the genre. So it gets points for trying – I’m sure this book spooked a lot of people back in the days when fallout shelters and “duck and cover” drills were still a thing.</p>
<h3><a href="https://www.goodreads.com/book/show/41447687-radicalized">Radicalized by Cory Doctorow</a><a name="radicalized-by-cory"></a></h3>
<p>I loved this book. I’ve been reading Cory Doctorow’s blog posts for years, and I’m surprised at what an effective storyteller he is. Think <em>Black Mirror</em>, but funnier and less bleak.</p>
<p>The two short stories that stood out the most to me were the first – about a toaster oven that refuses to toast “unlicensed” bread – and the third – about cancer survivors radicalized by an online forum.</p>
<p>The first story in particular feels plausible in a disturbing way, and it cuts to the core of some of <a href="https://medium.com/offline-camp/decentralization-is-not-enough-75b15b8bc230">the concerns I’ve expressed</a> about the ways that technology can be used to take more power away from those who are already powerless. For instance, consider <a href="https://www.theatlantic.com/technology/archive/2019/05/the-us-and-china-a-tale-of-two-surveillance-states/590542/">this (true) story</a> about renters in Brooklyn who are unable to stop their landlord from installing face-recognizing cameras. This story shows that Doctorow’s DRM toaster isn’t so much a vision of the future as it is an extrapolation of present trends. Which is what good science fiction is all about.</p>
<h2>Nonfiction</h2>
<h3><a href="https://www.goodreads.com/book/show/6604712-eating-animals">Eating Animals by Jonathan Safran Foer</a><a name="eating-animals-by-jonathan"></a></h3>
<p>A central fact about eating meat is that it’s much easier if you forget where it comes from. With this book I forced myself to take a hard look at where it comes from, and I found the results to be disturbing and appalling.</p>
<p>I don’t think it’s unnatural for humans to eat meat (my incisors are proof of that), but I do think that the modern factory farming system is immoral. It’s a form of industrial cruelty, systematized and magnified on a monstrous scale. Anyone who has owned a pet wouldn’t want it to experience even one minute of what these animals have to suffer every day of their lives.</p>
<p>If humans still did animal husbandry the old-fashioned way, on small-scale farms where the animals could live more-or-less decent lives, then I wouldn’t have a problem with eating animal products. What bothers me isn’t the way they die – it’s the way they live. Reading about the lives of egg-laying chickens and pigs in factory farms activates all my moral instincts and says in no uncertain terms, <em>This is wrong</em>. In fact, I think most meat-eaters would consider it wrong too, which is why they try to push it out of their minds.</p>
<p>I’d love to say that, after reading this book, I went fully vegan and never looked back. The truth is that I gave it a shot for a few weeks, found it too difficult, and then settled into a quasi-vegetarian/pescetarian thing, which is what I’ve been doing for the past decade or so anyway.</p>
<p>The main difference is that I have a better sense now of what kinds of foods actually reduce animal suffering. For instance: less dairy, more wild-caught fish. (I know; it’s surprising. Read the book.)</p>
<p>My relationship with food is still complicated, but at least this book has brought some facts and numbers to inform my decisions.</p>
<h3><a href="https://www.goodreads.com/book/show/41552709-the-uninhabitable-earth">The Uninhabitable Earth: Life After Warming by David Wallace-Wells</a><a name="the-uninhabitable-earth-life"></a></h3>
<p>I’ll admit: as recently as 2010, I probably would have described myself as a “climate change skeptic.” Not because I doubted the science (the consensus was clear at this point) but because I questioned whether the economic cost of combating climate change would outweigh the benefits of preventing it. India and China were rapidly developing – who was I to say that poor people in Kerala should live without air conditioning?</p>
<p>Like most everybody else, though, I’ve come around to the massive challenge posed by climate change. Living through two summer forest fires in Seattle, where people wore protective masks and the sky looked like a hazy Martian sunset, certainly helped change my mind. As did this book.</p>
<p>Before <em>The Uninhabitable Earth</em> I had also started reading <a href="https://www.goodreads.com/book/show/35791987-no-immediate-danger">Carbon</a> <a href="https://www.goodreads.com/book/show/36424258-no-good-alternative">Ideologies</a> by William T. Vollmann. They’re good books, but honestly they’re so long and dense and meandering that it’s hard to recommend them to anyone but the convinced climate activist. If you’re really interested in the physics, the numbers, and the nitty-gritty, then these books are for you.</p>
<p>Wallace-Wells’s book is different. It’s short, it’s punchy, and it encourages you to actually envision a world after global warming, and to let it hit you at a gut level. I imagine a book like this will inspire some great science fiction (<a href="https://en.wikipedia.org/wiki/Climate_fiction">cli-fi</a>?), which might do more to get people to care about climate change than all the facts and figures in the world. So for that, it’s a book I strongly recommend.</p>
<h3><a href="https://www.goodreads.com/book/show/17910054-the-sixth-extinction">The Sixth Extinction by Elizabeth Kolbert</a><a name="the-sixth-extinction-by"></a></h3>
<p>Kolbert’s book is another eye-opening look at humanity’s relationship with nature and where we fit into the grand arc of geologic history. I’ve had a longstanding interest in paleontology, and I find Kolbert’s defense of the <a href="https://en.wikipedia.org/wiki/Anthropocene">Anthropocene</a> (which is what this book amounts to) very compelling.</p>
<p>One thing that always puzzled me about climate change was why one or two degrees of average temperature, or a few percentage points of carbon dioxide in the atmosphere, would really be such a catastrophic event for humanity. Wasn’t the carbon dioxide level <a href="https://www.nature.com/articles/ngeo.2007.29">orders of magnitude higher during the Mesozoic</a>? Why would a few percentage points be our death knell?</p>
<p>What this book makes clear is that it’s not so much about the absolute numbers, but instead the <em>rate of change</em>. Earth has adapted to rapid changes before (such as an unlucky rendez-vous with an asteroid), but the recovery always takes a long time. Like, “longer than the human species has been around” long. Are we willing to trade 300 years of indulgence in fossil fuels for hundreds of thousands of years of getting the Earth’s ecosystem back on track?</p>
<p>If Wallace-Wells’s book hasn’t already bummed you out too much, then you should definitely pick this one up. It certainly helps put things in (geologic) perspective.</p>
</div>
</div>

<h2><a href="https://nolanlawson.com/2019/06/13/how-to-de-google-your-android-phone/" rel="bookmark">How to de-Google your Android phone</a></h2>
<p class="metadata">
	Posted by Nolan Lawson in <a href="https://nolanlawson.com/category/android/" rel="category tag">Android</a>.	Tagged: <a href="https://nolanlawson.com/tag/android-2/" rel="tag">android</a>, <a href="https://nolanlawson.com/tag/satire/" rel="tag">satire</a>.	<span class="feedback"><a href="https://nolanlawson.com/2019/06/13/how-to-de-google-your-android-phone/#comments">4 Comments</a></span></p>
<div class="entry">
<p>First, download a ROM from this Russian message board. It’s okay! You can totally verify the GPG signature. Allow yourself 30 minutes to remember how GPG works, then verify that forum poster LeetAndrej420 has indeed signed the file.</p>
<p>Next, root your Android phone. You will need to hold the volume-up and power buttons for ten seconds, then unplug from USB, then reboot a few times after you mess it up, then give up and download the Android dev tools.</p>
<p>After you figure out the Android <code>adb</code> and <code>fastboot</code> commands, you should see a friendly UI with green Courier text on a black background. Press the button that says, “I void my warranty and completely exonerate the OEM in the likely event that I am actually pwning myself by installing random software from the internet onto a tracking device I carry in my pocket every day.” But it’s okay. You trust Andrej, right?</p>
<p>Next you will need to install the “recovery” tool. Despite the name, this is actually the best way to brick your device. Luckily it is incredibly feature-rich, boasting 12 buttons on the home screen, including an “Advanced” button containing more buttons. These buttons will invite you to do things like “clear the Dalvik/ART cache,” which you totally know what that means.</p>
<p>When you download the recovery tool, make sure you get the right version for your phone! Of course, it’s not named after your phone’s brand name, but rather a cheeky internal name chosen by the OEM, like <a href="https://en.m.wikipedia.org/wiki/OnePlus_One">“bacon”</a>, <a href="https://en.m.wikipedia.org/wiki/OnePlus_5">“cheeseburger”</a>, or <a href="https://forum.xda-developers.com/wiki/Google/Device_Codenames">“mahimahi”</a>. The professionalism on display from all parties should fill you with confidence.</p>
<p>You will download the recovery tool from a site called SickWarez.biz. Use GPG to ensure that it’s signed by Andrej.</p>
<p>Once downloaded, go into recovery mode and install the ROM, being careful to press the one correct button out of 12, like a game of Minesweeper that will brick your phone if you lose. This will also factory-reset your device, which is fine because all your photos and contacts are backed up to your Google account… ah, right. You’ll want to do something about that.</p>
<p>Assuming you have successfully installed the ROM without turning your phone into a $700 doorstop, you can now install apps. Thankfully there is <a href="https://f-droid.org/">F-Droid</a>, which hosts all your favorite open-source apps. Wait, your favorite apps aren’t open-source? Well, at least it has Signal. Wait, <a href="https://github.com/signalapp/Signal-Android/issues/281#issuecomment-21762482">it doesn’t have Signal</a>?</p>
<p>Once you’ve installed the <a href="https://f-droid.org/en/packages/com.github.yeriomin.yalpstore/">Yalp Store</a>, which sideloads apps from Google Play in a way that may or may not be totally illegal and will get blocked by Google once they read this blog post and realize that it exists, you can now download some actually useful apps.</p>
<p>Thankfully, though, your personal data will be safe and secure from third-party developers, because these apps will not work. Be prepared for error messages like, “Please install Google Maps,” “Google Play Services required,” or “What kind of sicko has a Google phone without Google? What is wrong with you?”</p>
<p>After all this ceremony, you can now relax and enjoy your Google-free Android device. Note, though, that weather widgets, GPS, push notifications, and the majority of Android apps you rely on will not work. That said, there are some great note-taking apps! Plus SMS will still work. Good old SMS.</p>
<p>So now that you’ve successfully turned your $700 Android device into a glorified $30 Nokia flip phone, which may or may not be siphoning your passwords to a Ukrainian teenager, you can finally have a Google-free smartphone experience. Or you could just buy an iPhone.</p>
</div>

<h2><a href="https://nolanlawson.com/2019/06/02/one-year-of-pinafore/" rel="bookmark">One year of Pinafore</a></h2>
<p class="metadata">
	Posted by Nolan Lawson in <a href="https://nolanlawson.com/category/mastodon/" rel="category tag">Mastodon</a>, <a href="https://nolanlawson.com/category/web/" rel="category tag">Web</a>.		<span class="feedback"><a href="https://nolanlawson.com/2019/06/02/one-year-of-pinafore/#comments">2 Comments</a></span></p>
<div class="entry">
<p><img alt="Screenshot of Pinafore showing a compose input" class="aligncenter size-large wp-image-7522" data-attachment-id="7522" data-comments-opened="1" data-image-description="" data-image-meta='{"aperture":"0","credit":"","camera":"","caption":"","created_timestamp":"0","copyright":"","focal_length":"0","iso":"0","shutter_speed":"0","title":"","orientation":"0"}' data-image-title="Screenshot of Pinafore showing a compose input" data-large-file="https://nolanwlawson.files.wordpress.com/2019/06/screenshot_2019-06-01-toot-cafe-c2b7-home.png?w=570" data-medium-file="https://nolanwlawson.files.wordpress.com/2019/06/screenshot_2019-06-01-toot-cafe-c2b7-home.png?w=300" data-orig-file="https://nolanwlawson.files.wordpress.com/2019/06/screenshot_2019-06-01-toot-cafe-c2b7-home.png" data-orig-size="772,323" data-permalink="https://nolanlawson.com/2019/06/02/one-year-of-pinafore/screenshot_2019-06-01-toot-cafe-%c2%b7-home/" height="238" sizes="(max-width: 570px) 100vw, 570px" src="https://nolanwlawson.files.wordpress.com/2019/06/screenshot_2019-06-01-toot-cafe-c2b7-home.png?w=570&amp;h=238" srcset="https://nolanwlawson.files.wordpress.com/2019/06/screenshot_2019-06-01-toot-cafe-c2b7-home.png?w=570&amp;h=238 570w, https://nolanwlawson.files.wordpress.com/2019/06/screenshot_2019-06-01-toot-cafe-c2b7-home.png?w=150&amp;h=63 150w, https://nolanwlawson.files.wordpress.com/2019/06/screenshot_2019-06-01-toot-cafe-c2b7-home.png?w=300&amp;h=126 300w, https://nolanwlawson.files.wordpress.com/2019/06/screenshot_2019-06-01-toot-cafe-c2b7-home.png?w=768&amp;h=321 768w, https://nolanwlawson.files.wordpress.com/2019/06/screenshot_2019-06-01-toot-cafe-c2b7-home.png 772w" width="570"/></p>
<p><a href="https://pinafore.social">Pinafore</a> is a standalone web client for Mastodon, which recently hit <a href="https://github.com/nolanlawson/pinafore/releases/tag/v1.9.0">version 1.9.0</a>. Here are some notable new features:</p>
<ul>
<li><a href="https://github.com/nolanlawson/pinafore/pull/1256">Wellness settings</a></li>
<li><a href="https://github.com/nolanlawson/pinafore/pull/1253">An option to disable infinite scroll</a></li>
<li><a href="https://github.com/nolanlawson/pinafore/pull/1226">Timeline and notification filters</a> (added in v1.8.0)</li>
</ul>
<p>It’s been about a year since I first launched Pinafore. So I’d like to reflect on where the project came from, and where I hope to take it.</p>
<h2>Background</h2>
<p>In 2017, I was in a funk. I had stopped contributing to the <a href="https://pouchdb.com">PouchDB</a> project largely <a href="https://nolanlawson.com/2017/08/23/burnout-and-twitter-fatigue/">due to burnout</a>, and for various reasons I eventually <a href="https://nolanlawson.com/2018/09/09/moving-on-from-microsoft/">left my job at Microsoft</a>. In the meantime, I had become enamored of <a href="https://joinmastodon.org">Mastodon</a> and even contributed to it, but I was feeling restless and looking for a new project.</p>
<p>The Mastodon codebase is extremely well-written. I’m convinced that Eugen Rochko is some kind of savant. However, I never took much of a liking to React, and I found it difficult to fix some fundamental problems in the Mastodon UI, such as offline support or the occasionally jerky scrolling. I also really missed the single-column layout of Twitter (I was never a Tweetdeck fan).</p>
<p>So the idea came to me to create my own Mastodon web client. I had been working on web sites for years, but aside from some small prototypes, I had never built an entire web app by myself. This was an opportunity to test some of my ideas about how a web app “should” be, leveraging my experience in web performance and standards. Also, I wanted to teach myself about accessibility, which I had never really studied before.</p>
<p>I knew I wanted to use <a href="https://svelte.technology/">Svelte</a>, because I agreed with <a href="https://svelte.dev/blog/frameworks-without-the-framework">Rich Harris</a> and <a href="https://tomdale.net/2017/09/compilers-are-the-new-frameworks/">Tom Dale</a> that JavaScript frameworks should focus less on being runtime APIs and more on being compilers. Incidentally, I was at the same talk by <a href="https://jed.is/">Jed Schmitt</a> that Rich mentions in <a href="https://www.youtube.com/watch?v=qqt6YxAZoOc">this video</a>, and it blew my mind as much as it blew his. (The difference between Rich and me is that he actually went off and built a whole framework based on it!)</p>
<p>I started working on Pinafore at the end of December 2017, and released it in April 2018. So after 18 months of development, I’d like to consider where Pinafore has done well and where it can improve.</p>
<h2>Success metrics</h2>
<p>Pinafore doesn’t have any trackers on it, so I don’t know how many people are using it. Sure, I could use a privacy-respecting tracker like <a href="https://github.com/usefathom/fathom">Fathom</a>, but the Mastodon community is pretty allergic to any kind of tracking, so I’ve been hesitant to add it. In any case, I don’t really care, because I would work on Pinafore regardless of how many people are using it.</p>
<p>However, I do get a trickle of questions and bug reports about Pinafore, and the #Pinafore hashtag is pretty active. I’ve also heard from several folks that it’s their preferred Mastodon interface. The reasons they give are usually one of the following:</p>
<ul>
<li><strong>Accessibility</strong>: I’ve focused a lot on making Pinafore work well with keyboard navigation and screen readers. (<a href="https://www.marcozehe.de">Marco Zehe</a>‘s guidance really helped!)</li>
<li><strong>Design</strong>: the single-column layout of Pinafore is a key differentiator with the Mastodon frontend (although <a href="https://github.com/tootsuite/mastodon/pull/10847">not for long</a>).</li>
<li><strong>Instance-switching</strong>: people who juggle multiple accounts on different instances don’t necessarily want one browser tab for each.</li>
</ul>
<p>My favorite user testimonial, though, is from my wife. She told me, “I like Pinafore because it never loses my place in the timeline.” (Much of my motivation for working on Pinafore can be credited to “wife-driven development” – I like making her happy!)</p>
<p>So this confirms that I’ve achieved at least some of the goals from the <a href="https://nolanlawson.com/2018/04/09/introducing-pinafore-for-mastodon/">Pinafore introductory blog post</a>. Although notably, offline support is rarely mentioned, but I’ll get to that later.</p>
<h2>Collaboration</h2>
<p>Pinafore has also benefited from <a href="https://github.com/nolanlawson/pinafore/graphs/contributors">a lot of community contributions</a>. I’d like to specifically thank:</p>
<ul>
<li><a href="https://github.com/sgenoud">Steve Genoud</a>, who improved the media UI as well as many other things.</li>
<li><a href="https://github.com/SpankyWorks">Spanky</a>, who created the first dark theme.</li>
<li><a href="https://github.com/mlcdf">Maxime Le Conte des Floris</a>, who contributed more great dark themes.</li>
<li><a href="https://github.com/codl">codl</a>, who fixed lots of UI bugs.</li>
<li><a href="https://github.com/uiri">Will Pearson</a>, who helped out with Pleroma support.</li>
<li><a href="https://github.com/sorin-davidoi">Sorin Davidoi</a>, who implemented web push notifications.</li>
<li><a href="https://github.com/szermatt">Stephane Zermatten</a>, who added keyboard shortcuts.</li>
<li><a href="https://github.com/stanclai">stanclai</a>, who reduced the Docker size.</li>
</ul>
<p>And of course <a href="https://github.com/nolanlawson/pinafore/graphs/contributors">everyone else</a> who contributed. Thank you so much!</p>
<p>There are some challenges with building a dev community around Pinafore. The app is implemented using <a href="http://svelte.technology/">Svelte</a> v2 and <a href="http://sapper.svelte.technology/">Sapper</a>, which unfortunately causes two downsides in terms of onboarding: 1) Svelte isn’t a very well-known framework, and 2) Svelte v2 is incompatible with Svelte v3, and there’s no upgrade path currently.</p>
<p>I’ll have to continue grappling with these challenges, but for now I’m very satisfied with Svelte v2. It’s fast, lightweight, and does everything I need it to. So I’m not in a big hurry to upgrade.</p>
<p>And oh yeah: Svelte really is lightweight. Pinafore only loads 32KB of compressed JavaScript for the landing page, and 137KB for the Home timeline. The <a href="https://pinafore.social/report.html">total size of all JS assets</a> is under 300KB compressed (&lt;1MB raw). It gets <a href="https://www.webpagetest.org/lighthouse.php?test=190602_YG_76a2322c18e5572a637f5768200e01bb&amp;run=3">a perfect 100 score from Lighthouse</a>.</p>

<h2>Future plans</h2>
<p>My first goal with Pinafore is completeness. Even though I’ve been working on it for over a year, there are still plenty of missing features compared to the Mastodon frontend. And although the gap has been narrowing, Mastodon itself hasn’t stopped innovating, so there’s always new stuff to add. (Polls! Blurhash! Keybase! Does Eugen ever sleep?)</p>
<p>Beyond that, I’d like to start focusing on features that make Pinafore a more pleasant social media experience. One of the virtues of decentralized social media is that we can experiment with features that give people control over their social media experience, even if it hampers addictiveness or growth. To that end, I’ve added a set of <a href="https://github.com/nolanlawson/pinafore/issues/1192">wellness features</a>, inspired by Tristan Harris’s <a href="https://humanetech.com/">Center for Humane Technology</a>. I’ll probably tweak and expand these features as feedback rolls in.</p>
<p>I’d also like to improve offline support. Even though Pinafore does have an offline mode, and even though it uses a Service Worker to cache static assets, it’s not very <a href="http://offlinefirst.org/">offline-first</a>. Instead, it uses offline storage more as a fallback for when the network fails, rather than as the primary source of truth.</p>
<p>Given my background working on offline-first technology and advocating for it, I find this a bit disappointing. But it turns out that it’s really difficult to implement an offline-first social media UI. How do you deal with offline writes? How do you handle the gap between fresh content and stale content within the same timeline? These are not easy questions, and for the most part I’ve punted on them. But Pinafore can do better.</p>
<h2>Conclusion</h2>
<p>Pinafore is a passion project for me. It gives me something interesting to do on weekends and evenings, and it teaches me a lot about how the web platform works.</p>
<p>I also see Pinafore as an opportunity to provide more options to the Mastodon community, and to prove that you don’t have to treat Eugen as a gatekeeper for every minor UI tweak you’d like to see in Mastodon. Mastodon is decentralized; let’s decentralize the interface!</p>
<p>I have every intention to keep working on Pinafore, and I’m curious to know where you think it should go next.</p>
